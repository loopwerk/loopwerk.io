# uv is fantastic, but its package management UX is a mess

Astral's [uv](https://docs.astral.sh/uv/) has completely taken over the Python world, and for good reason: it's very fast, makes installing different Python versions super easy, and it replaces a bunch of tools. I've written [multiple articles](/articles/tag/uv/) about it in the past two years.

Creating a new Python project using uv, and adding your first dependencies to it, is very smooth. But once you move beyond this initial setup, uv's CLI starts to feel surprisingly clunky in my opinion.

## Finding outdated packages

In my JavaScript projects, if I want to see what needs an update, I run:

```shell-session
$ pnpm outdated
```

That gives me a clean and clear list of outdated versions. In uv, there is no simple `outdated` command. Instead, there are two different commands, both of which are a mouthful. Let's start with this one:

```shell-session
$ uv tree --outdated --depth 1
```

The problem is that this doesn't only show you the outdated packages; it shows you all packages, and you have to scan the list for annotations that an update is available. With a big list of dependencies, that becomes pretty tedious.

The better command to use is actually this one:

```shell-session
$ uv pip list --outdated
```

This one only shows you packages that are actually outdated, but there is no `depth` parameter so it also shows you deeply nested dependencies, which I usually don't care about at all. And why does this command live under the `pip` namespace? Why is there no useful top-level `outdated` command?

Poetry isn't much better with its command `poetry show --outdated`, but at least it only shows actual outdated packages.

## Unsafe version constraints by default

This is uv's biggest philosophical difference compared to pnpm and Poetry, and in my opinion, at least when it comes to applications, a risky choice.

When you add a package using `pnpm add`, it writes it to `package.json` using the caret requirement (`^1.23.4`). The caret at the beginning means that any 1.x.x version is allowed, but it will not update to 2.0.0.

Poetry does the same by default, using a format like `>=1.23.4,<2.0.0`.

With both pnpm and Poetry, this means that updates are safe by default. You can run `pnpm update` or `poetry update` as often as you want, and have a reasonable expectation that nothing will break - assuming your dependencies respect semantic versioning (or SemVer for short).

On the other hand, when you add a package with uv, it's added without an upper bound: `>=1.23.4`. This means that installing updates is unsafe by default. You're opted into every upcoming breaking change!

To be fair: when you publish a library to PyPI, the lack of upper bounds is 100% correct. Let's say I create a Django library and it depends on Django. If my library pinned the bounds to `>=6.0.0,<7.0.0`, it would be unusable when Django 7 is released. It would block a user of the library from using Django 7.

But for applications, where you're the end node in the dependency graph, upper bounds have no real downside. And they do protect you from surprise major version bumps with all of their breaking changes! It seems to me that uv's default serves the library case, not the application case.

## Updating packages

The thing I dislike most about uv is not the lack of a top-level `outdated` command, but the poor usability of updating outdated packages. It feels like this process was designed for machines, rather than humans.

When you want to update all your dependencies in pnpm or Poetry, it's a simple `pnpm update` or `poetry update`. In uv you use `uv lock --upgrade`.

First of all, I again wonder why there is no top-level command for this, but let's look past that and focus on the real problem. Because of the missing upper bounds, `uv lock --upgrade` will upgrade every single package to the latest version, ignoring SemVer. Good luck with that, better hope there are no breaking changes anywhere.

So, once you realize that this command is way too risky, you'll want to upgrade only specific packages. So you find the outdated packages using one of the two subpar commands for that, and then run a command like this:

```shell-session
$ uv lock --upgrade-package pydantic --upgrade-package httpx --upgrade-package uvicorn
```

Why do I have to repeat the `--upgrade-package` flag for every item? This is such a hassle when you want to upgrade multiple dependencies. I don't understand why the UX of uv's commands is so poor.

## Adding upper bounds

So far I've been dealing with the lack of upper bounds by manually editing `pyproject.toml`, and adding them to all my top-level dependencies. That makes `uv lock --upgrade` much safer to run.

The good news is that uv has recently introduced a `--bounds` option to the `uv add` command:

```shell-session
$ uv add pydantic --bounds major
```

This adds the dependency with the safer `>=2.13.4,<3.0.0` constraint. Even better, you can add this to `pyproject.toml` and then you don't have to remember to use `--bounds major`:

```toml
[tool.uv]
add-bounds = "major"
```

This is still a preview feature, but it seems to work well. I hope that for applications it becomes the default option, instead of something you have to know about and opt into.

## What I'd like to see

As I said before, I really do love uv for its speed and features. But the developer experience for maintaining a Python project could be a lot better - I think we need more top-level commands, with better defaults. Honestly their entire CLI should probably be overhauled. There are [too many commands](https://docs.astral.sh/uv/reference/cli/) in too many namespaces, some of which do kind of the same but in slightly different ways.
